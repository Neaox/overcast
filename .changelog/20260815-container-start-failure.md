*. [elasticache] a create whose container the Docker daemon refuses now reports the failure instead of leaving the cache in `creating` forever. This is the third thing that can happen to a create and the only one left unanswered: a deployment with no Docker settles the record immediately, a container that comes up but never answers is settled by the readiness watch, and a container that could not be built at all fell between them — the start goroutine logged a warning and returned, and the readiness watch that would have owned the record from there is only scheduled once the start succeeds, so nothing was left that would ever move it. A cache cluster now settles in `incompatible-network` and a replication group and a serverless cache in `create-failed`, the same terminal statuses each shape already used when its engine never answered, with the daemon's own error recorded as the reason. Both the form-encoded and the typed create paths are fixed, so the status no longer depends on which wire protocol the caller's SDK negotiated
* [msk] the same for a cluster whose broker container cannot be built: it reaches `FAILED` with the daemon's error in `stateInfo`, which `DescribeCluster` and `DescribeClusterV2` both return, rather than sitting in `CREATING` with nothing coming. A cluster that is already `ACTIVE` when a reconcile or Docker-event start fails is left alone
* [cloudformation] a stack whose ElastiCache or MSK resource cannot get a container now fails on the reason rather than on a timeout. The resource waits added for these services classify all four of these statuses as failures already, so a failure that is reported at all is reported the moment it happens instead of after the full stabilization budget — fifteen minutes for a cache and forty-five for a cluster, spent waiting on a record nothing was ever going to move
