# Full-emulation priority — which services/operations get Tier 2, and in what order

> Status: proposal, 2026-08-03. Owner: TBD.
> Tracking issue: #484; sub-issues per item.
> Scope: everything Tier 2-eligible. [services-never-emulated.md](./services-never-emulated.md) (if present)
> defines what is permanently out of scope; this document's ranking starts from
> [inert-tier-rollout.md](./inert-tier-rollout.md)'s Tier 1 floor (every registered service reaches
> correct-shape metadata CRUD) and orders the climb from there to Tier 2 (full behavioral emulation).
> Measurement plumbing is covered by [compat-coverage-modelgen.md](./compat-coverage-modelgen.md).
> Separately-tracked Tier-2 work (EFS data plane, still in flight; DynamoDB GSI, closed 2026-08-03) is
> **not replanned here** — see §5.

Tier vocabulary used throughout (repo-wide, not invented for this doc):

- **Tier 0** — protocol-correct `501 NotImplemented`. The operation is recognized and routed but does nothing.
- **Tier 1 ("inert")** — metadata CRUD with correct shapes. Store it, echo it back, satisfy CDK/CloudFormation
  provisioning and SDK calls. No side effects, no cross-service delivery, no state machine.
- **Tier 2 ("full emulation")** — behavior matches AWS closely enough that an application built against it
  and then pointed at real AWS keeps working: side effects fire, state transitions happen, other services
  observe the effects.

## 0. How this was built (method note, not for the impatient reader)

STATUS.md's three hand-written tables ("Comprehensive" / "Core operations" / "Minimal / Stub") are **stale
prose** — they were checked against the codebase for this plan and found to both mis-state at least one
number and omit 16 registered services entirely. Every claim below about current implementation depth is
instead sourced from `internal/capabilities/all.gen.go` (code-generated by `go run -tags dev ./cmd/capgen`,
kept fresh by `make generate-caps` / `make check-caps` in CI) and from reading the handlers it describes.
Discrepancies found are logged in §6.

`internal/capabilities/all.gen.go` tags every registered operation with a `Status`: `StatusSupported`,
`StatusUnsupported` (registered, returns 501), or `StatusInert` (registered, does something, but the
something is metadata-only — this is the capability registry's own name for Tier 1). Aggregate as of this
audit: **1,116 Supported, 154 Unsupported, 48 Inert**, across 1,318 rows / ~50 services. That Inert count is
concentrated in exactly five services that are Tier 1 end-to-end — see §5.3.

## 2. Scoring rubric

Six factors, weighted. Each candidate is scored 1–5 on the four "raw" factors (higher is better throughout,
including for the two cost/risk factors, which are pre-inverted so the arithmetic stays additive):

```
score = 0.25 × usage        (external demand signal)
      + 0.25 × leverage     (how many other local architectures this unblocks)
      + 0.20 × fit          (does faithful local behavior matter, or is inert good enough forever)
      + 0.15 × (6 − cost)   (S=1 M=2 L=3 XL=5 on the raw scale, inverted so cheap scores high)
      + 0.10 × dep_ready    (are the services this depends on already mature)
      + 0.05 × (6 − risk)   (fidelity risk: would half-faithful behavior actively mislead)
```

Rationale for the weights: **usage** and **leverage** dominate (0.25 each) because this is a prioritization
exercise, not an estimation exercise — the question is "what should be next," and value swamps cost at the
top of a backlog. **Fit** is weighted 0.20 and gates hard at zero for anything where local fidelity is
structurally meaningless (edge/global infrastructure, billing, multi-account) — no amount of usage buys back
a service where "full emulation" doesn't mean anything on one machine. **Cost** (0.15) and **dependency
readiness** (0.10) are real but secondary: Overcast has repeatedly shown that features which reuse existing
plumbing (Docker container lifecycle, the event bus, the clock-driven sweeper pattern DynamoDB TTL and
Lambda provisioned-concurrency already use) land fast, so a nominally "large" item next to mature
dependencies is cheaper than the S/M/L/XL label alone suggests. **Fidelity risk** (0.05) is the smallest
weight but a veto in practice: see §2.1.

Factor definitions:

- **Usage (1–5)** — external evidence: SDK package popularity, IaC tool prevalence, competitor paywall
  placement, general serverless-architecture ubiquity. See §4 for what evidence was actually found.
- **Leverage (1–5)** — dev-loop unlock effect. A 5 means "many application shapes are unreachable locally
  without this" (Step Functions execution: every workflow app; EventBridge fan-out: every event-driven
  architecture). A 1 means "improves fidelity for users of this one service only."
- **Fit (1–5)** — does correct *behavior* (not just correct *shape*) matter in a single-node, no-billing,
  no-multi-AZ dev loop? Messaging/compute/storage/auth score high. Edge/global-routing, DDoS protection,
  billing metering, and multi-account governance score low regardless of how important they are on real AWS.
- **Cost (S/M/L/XL → 1/2/3/4/5 before inversion)** — informed by what already exists in `internal/services/`:
  S = extend an existing switch/handler; M = new sub-package reusing existing infra (event bus, Docker
  lifecycle, clock-driven sweeper); L = new stateful engine (an interpreter, a policy evaluator); XL = new
  engine plus new infra this repo doesn't have at all (e.g. a real scheduler with preemption).
- **Dependency readiness (1–5)** — are the services this item delivers *to* or reads *from* already Tier 2?
  Fan-out to Lambda/SQS/SNS scores high because those are Comprehensive already; fan-out to a service that
  is itself still Tier 1 scores low because you'd be building on sand.
- **Fidelity risk (1–5, inverted)** — could a half-faithful implementation be *worse than leaving it inert*?
  IAM enforcement is the textbook case: turning it on by default would break every currently-passing
  compat suite and every user's existing local stack, for a "no" that real AWS wouldn't necessarily give
  (the policy shapes are usually more permissive than a naive evaluator assumes). High risk doesn't
  disqualify an item — it dictates the definition-of-done (opt-in flag, evaluate-but-don't-enforce mode
  first, etc.), which is why the DoD sketches in §5 call this out explicitly wherever it applies.

### 2.1 The fidelity-risk veto

Two shapes of "worse than inert" recur across this backlog and are called out wherever they apply:

1. **Enforcement that changes default behavior.** IAM, API Gateway throttling, and WAF rule evaluation all
   have the property that "on" can turn a previously-working local stack into one that gets `403`/`429`
   responses it didn't get before, for reasons that may not even match what real AWS would decide (the
   evaluator is necessarily a subset of AWS's). DoD for all three: ship policy/limit *evaluation and
   reporting* first (what would happen), gate actual enforcement behind an explicit opt-in flag, default
   OFF.
2. **Partial protocol behavior that looks complete.** A Step Functions engine that handles `Task`/`Pass`/
   `Choice` but silently no-ops on `Map`/`Parallel`/`.sync` integrations is worse than today's honest
   immediate-`SUCCEEDED` stub, because it invites an application to depend on control flow that doesn't
   run. DoD requires either full ASL state-type coverage or a loud `501`/explicit "not implemented" for the
   unsupported state types — never a silent pass-through.

## 3. Scored backlog, by wave

Waves are themes, roughly quarter-sized (2–4 items each, sequenced within a wave by dependency, not by
score — items in the same wave are meant to land together). Scores use the §2 formula; components shown as
`usage/leverage/fit/cost/dep/risk` (cost and risk already inverted, 1–5 raw before the `6 −` in the formula
is applied — shown here as the pre-inversion S/M/L/XL and risk label for readability).

### Wave 1 — Event & workflow correctness

The theme: Overcast can create every resource in an event-driven or workflow architecture, but roughly a
third of the *wiring* between them is a no-op. This wave is "make what's already provisioned actually run."

**1. EventBridge Rules target fan-out** — Core → Comprehensive
Score: usage 5, leverage 5, fit 5, cost M, dep-ready 5, risk low → **highest in the backlog**.
Current state: `PutTargets`/`PutEvents` deliver to SQS targets and scheduled ECS task targets only
([eventbridge/capabilities_dev.go](../../internal/services/eventbridge/capabilities_dev.go) notes on
`PutEvents`: "delivers matching rules to SQS targets"). Real EventBridge has ~20 target types; the ones
that matter for a local dev loop are Lambda, SNS, Step Functions, Kinesis, and Firehose — all Tier-2 or
soon-to-be-Tier-2 services already, so delivery is "invoke the same internal interface Scheduler already
calls" (Scheduler already fires Lambda async-invoke, SQS enqueue, and SNS publish —
[scheduler/service.go:13](../../internal/services/scheduler/service.go) — making this largely a matter of
reusing that dispatch code from the rule-matching path instead of rebuilding it).
Definition of done:
- `PutTargets` accepts Lambda, SNS, Step Functions (`StartExecution`), Kinesis (`PutRecord`), and Firehose
  (`PutRecord`) target ARNs and validates them at add-time (matching AWS's synchronous ARN-shape check).
- `PutEvents` delivery matches each event against rules on the target bus, evaluates the rule's event
  pattern (already implemented for existing SQS delivery), and invokes the correct sink for every matched
  target type, not just SQS.
- Input transformers (`InputPath`, `InputTransformer`) apply before delivery, matching the SQS path's
  existing behavior if it has any, or added if not.
- Failed deliveries respect `RetryPolicy`/DLQ config on the target if set; otherwise are dropped with a
  logged warning (matching current SQS-target failure handling).
- `CreateArchive`/`StartReplay`/`CreateConnection` (API destinations) stay out of scope for this item — see
  Wave 4.
Dependencies: none blocking — Lambda, SNS, SQS are all Comprehensive; Step Functions execution (this same
wave, item 3) should land first or concurrently so the Step-Functions target type has somewhere real to go.

**2. SNS → Lambda delivery** — bug-fix sized, ships independently and first
Score: usage 4, leverage 3, fit 5, cost S, dep-ready 5, risk low.
This is not a new tier, it's closing a hole in an already-Comprehensive service: `Subscribe` documents and
accepts protocol `lambda` but `Publish`'s delivery switch
([sns/handler_publish.go:260-383](../../internal/services/sns/handler_publish.go)) has no case for it, so
messages are silently dropped rather than erroring — the worst possible failure mode (§2.1 shape 2, even
though this isn't new work, the existing behavior already violates the principle). Fix: add a `case
"lambda"` that does an async `Invoke` against the subscribed function, matching the SNS event payload shape
Lambda expects (`Records[].Sns`). Cheap, ships as a standalone patch, doesn't need to wait for Wave 1 item 1.

**3. Step Functions execution engine** — Minimal-stub → Core
Score: usage 4, leverage 5, fit 4, cost XL, dep-ready 4, risk medium (see §2.1 shape 2) → **second-highest
by leverage, held back only by cost**.
Current state: `CreateStateMachine`/`DescribeStateMachine`/`ListStateMachines`/`DeleteStateMachine` are
real CRUD; `StartExecution` records an execution row and sets it `SUCCEEDED` immediately
([stepfunctions/handler.go:224](../../internal/services/stepfunctions/handler.go),
[typed_logic.go:179](../../internal/services/stepfunctions/typed_logic.go)) — no ASL is parsed or run, so
`DescribeExecution`, `GetExecutionHistory`, and any test asserting on execution output are all fiction
today.
Definition of done (staged, not all-or-nothing — land Standard/synchronous first):
- ASL parser for the standard state types: `Pass`, `Task`, `Choice`, `Wait`, `Succeed`, `Fail`, `Parallel`,
  `Map` (inline `ItemsPath` iteration; `ItemProcessor`/distributed map is Wave-4-or-later scope).
- `Task` resource integrations for what's already Tier 2 in this repo: Lambda `Invoke` (both
  request-response and `.sync`), SQS `SendMessage`, SNS `Publish`, DynamoDB `PutItem`/`GetItem`/
  `UpdateItem`. Anything else is a loud "resource type not supported" error, not a silent skip.
  `.waitForTaskToken` is Wave-4-or-later — needs `SendTaskSuccess`/`SendTaskFailure`/`SendTaskHeartbeat`,
  currently unregistered ops.
- `GetExecutionHistory` emits real state-transition events in AWS's event-type vocabulary
  (`ExecutionStarted`, `TaskStateEntered`, `TaskScheduled`, `TaskSucceeded`, …) so
  step-functions-local-style test assertions work unmodified.
- Retry/Catch fields on `Task` states honored (this is most of what makes Step Functions worth testing
  locally — failure-handling logic that's otherwise untestable without hitting real AWS and inducing a
  real failure).
- Execution runs synchronously in-process on `StartExecution` initially (matches the existing single-node,
  deterministic-clock architecture) — `StartSyncExecution` for Express workflows can reuse the same
  interpreter directly.
Dependencies: none hard-blocking, but Task integrations are only as good as the target services — this is
why the item sits in the same wave as EventBridge fan-out (both need "invoke Lambda/SQS/SNS/DynamoDB from
inside an event/workflow handler," which is worth building once, shared).

**4. Pipes: sources/targets beyond DynamoDB Streams→SQS** — Minimal-stub → Core
Score: usage 2, leverage 3, fit 4, cost M, dep-ready 3 (waits on item 1), risk low. Sequenced last in this
wave specifically because it shares the target-dispatch code Wave 1 item 1 builds for EventBridge Rules —
building it twice is the wrong order. Definition of done: Kinesis stream and SQS queue as additional
sources; Lambda, Step Functions, and EventBridge bus as additional targets; enrichment step (optional
Lambda invoke between source and target).

### Wave 2 — Enforcement & guardrails

The theme: three already-Comprehensive-or-Core services store limits/policies they never check. This is
the wave where the §2.1 fidelity-risk veto matters most — every item here ships in report-only/opt-in mode.

**5. IAM policy evaluation** — Core, no enforcement → Core, opt-in enforcement
Score: usage 5, leverage 4 (gates correctness testing across every other service, but doesn't unlock new
*architectures* the way Step Functions does — hence 4, not 5), fit 4, cost L, dep-ready 5, risk high (§2.1
shape 1).
Definition of done:
- A real policy evaluator: parse the IAM JSON policy grammar (`Effect`, `Action` with wildcards, `Resource`
  ARN matching including wildcards, `Condition` for the common operators), explicit-deny-wins, evaluate
  identity + resource + SCP-shaped inputs the way AWS's algorithm does.
- `SimulatePrincipalPolicy`/`SimulateCustomPolicy` return real `allowed`/`explicitDeny`/`implicitDeny`
  results instead of always-allow — this alone is useful without touching request-time enforcement and
  should ship first, since it's zero fidelity-risk (nothing currently depends on simulation being
  permissive).
- Request-time enforcement is a separate, explicitly opt-in mode (`OVERCAST_IAM_ENFORCE=1` or equivalent):
  when off (default), every request behaves as today; when on, requests are evaluated against the calling
  principal's attached/inline policies before reaching the service handler, returning AWS-shaped
  `AccessDenied` on explicit or implicit deny.
- Scope the first cut to the services developers most often get wrong locally: S3 bucket policies +
  IAM identity policies together (the most common real-AWS `AccessDenied` source), Lambda resource
  policies, SQS/SNS resource policies.
Dependencies: none blocking; this is additive to every other service and doesn't need any of them to change.

**6. API Gateway usage-plan throttle/quota enforcement** — Comprehensive, stub gap → Comprehensive, complete
Score: usage 3, leverage 2, fit 3, cost S, dep-ready 5, risk medium (§2.1 shape 1, smaller blast radius than
IAM since it's scoped to API Gateway only).
Definition of done: `store.go`'s `ThrottleSettings`/quota are read at request time in
`ExecuteRestAPI`/`ExecuteV2API`; over-limit requests get AWS's `429 TooManyRequestsException`; default
behavior unchanged unless a usage plan with a throttle/quota is actually attached to the calling API key
(i.e., this is opt-in by construction — no flag needed, since the enforcement only activates on resources
the user explicitly configured a limit for).

**7. CloudWatch Alarms auto-evaluation** — Core, manual-only → Core, complete
Score: usage 3, leverage 3 (mostly valuable as a dependency for item 8), fit 4, cost M, dep-ready 4, risk
low (this one is additive — nothing currently depends on alarms staying manually-set).
Definition of done: a clock-driven evaluator (same pattern as the DynamoDB TTL sweeper and Lambda
provisioned-concurrency warmer) that, on each `PutMetricData` call or on a periodic tick, evaluates every
alarm watching that metric against its threshold/`ComparisonOperator`/`EvaluationPeriods`, and transitions
`StateValue` through `OK`/`ALARM`/`INSUFFICIENT_DATA` with a `StateReason`, publishing an `EventBridge`
event and (if configured) an SNS notification on transition — matching real CloudWatch's actual side
effects, not just the stored field.

**8. Auto Scaling real reconciliation** — Tier 1 (inert, 19/19 ops) → Core
Score: usage 3, leverage 3, fit 3, cost L, dep-ready 3 (stronger once item 7 lands), risk low (adding
behavior to a service with zero live behavior today carries no regression risk).
This is the cleanest "promote a wholly-inert service" candidate in the backlog — all 19 registered
operations are `StatusInert` today (`internal/capabilities/all.gen.go`), meaning there is no existing
behavior to preserve compatibility with.
Definition of done:
- A reconciliation loop (mirrors the ECS service reconciler already in `internal/services/ecs`): on
  `CreateAutoScalingGroup`/`UpdateAutoScalingGroup`/`SetDesiredCapacity`, launch/terminate EC2 instances
  via the existing EC2 service to converge actual instance count on `DesiredCapacity`, respecting
  `MinSize`/`MaxSize` for the group.
- `PutScalingPolicy` (target-tracking and step scaling) evaluates against CloudWatch alarm state (item 7)
  and adjusts desired capacity accordingly.
- Lifecycle hooks (`PutLifecycleHook`) actually pause instance launch/terminate for the hook's timeout,
  emitting the EventBridge lifecycle-action event real Auto Scaling emits.
Dependencies: EC2 (Comprehensive already) for instance launch/terminate; CloudWatch Alarms (item 7) for
alarm-driven policies — desired-capacity-only scaling can ship without it.

### Wave 3 — Storage & secrets completeness

The theme: close out well-known, specifically-named gaps in services that are otherwise Comprehensive —
high user-visible payoff per unit of work because these are "the one thing missing" in services people
already trust.

**9. S3 lifecycle rules** — Comprehensive, stub gap → complete
Score: usage 4, leverage 2, fit 4, cost M, dep-ready 5, risk low.
`GetBucketLifecycleConfiguration`/`PutBucketLifecycleConfiguration`/`DeleteBucketLifecycle` are pure `501`
stubs today (`internal/capabilities/all.gen.go` s3 rows). Definition of done: store lifecycle rules;
a clock-driven sweeper (same pattern as DynamoDB TTL) expires/deletes objects past their `Expiration`
rule and (optionally) tags objects past a `Transition` rule with a synthetic storage-class marker rather
than actually moving bytes to Glacier semantics (real Glacier retrieval delay emulation is explicitly out
of scope — see §6 non-goals). This is a very common CDK default (`autoDeleteObjects: true` on log buckets,
temp/staging buckets with TTL) that currently provisions silently and then does nothing.

**10. Secrets Manager rotation + resource policies** — Core (14/21) → Comprehensive
Score: usage 3, leverage 2, fit 4, cost M, dep-ready 5, risk low.
`RotateSecret` is "Config only (no Lambda invocation)"; `Get/Put/Delete/ValidateResourcePolicy` are all
501 stubs (`internal/capabilities/all.gen.go` secretsmanager rows — 14 Supported / 7 Unsupported today;
**STATUS.md's hand-written "11 of 21" is stale**, see §6). Definition of done: `RotateSecret` actually
invokes the configured rotation Lambda with the four-step AWS rotation protocol
(`createSecret`/`setSecret`/`testSecret`/`finishSecret` steps via `Invoke`), matching the real state
machine AWS's rotation Lambda blueprint expects; resource-policy CRUD stored and returned (enforcement
piggybacks on IAM work, item 5, if that lands — otherwise stored-but-not-enforced is still strictly better
than 501).

**11. DynamoDB PartiQL (`ExecuteStatement`/`ExecuteTransaction`/`BatchExecuteStatement`)** — not
registered at all today → Core addition
Score: usage 2, leverage 2, fit 4, cost M, dep-ready 5, risk low.
Sequenced explicitly **after** the [dynamodb-gsi-design.md](./dynamodb-gsi-design.md) work
finishes, not because PartiQL needs the new index structure to *exist*, but because it's the same
query-planning surface (`WHERE` clause → key-condition-or-scan decision) and building it twice against two
different storage backends is wasted work. **That dependency is satisfied as of 2026-08-03**: GSI phases
1–3 and all three deferred follow-ups (LSI routing, ConsistentRead-on-GSI validation, parallel-scan
segmentation) are closed, so this item is now free to start. Whoever picks it up inherits a settled query
path to build against — `queryTyped`'s index branches and `scan_segments.go` are the shapes a PartiQL
`WHERE` clause should compile down onto rather than a second planner.

   ([datadoghq.com/state-of-serverless](https://www.datadoghq.com/state-of-serverless/), general finding,
   exact report year not confirmable from search snippets — treated as directional, not precise.) Used only

4. **CDK Construct Hub / Terraform AWS provider popularity rankings** — searched, but neither surfaced

   the `aws` provider's overall dominance — 6.5B+ cumulative downloads, per HashiCorp's November 2025

5. **Confidence summary**: usage scores for compute/storage/messaging primitives (S3, Lambda, SQS, SNS,

## 6. STATUS.md discrepancies found during this audit

Per instruction, STATUS.md's hand-written tables were verified against `internal/capabilities/all.gen.go`
and the handlers themselves rather than trusted. Findings:

1. **Secrets Manager op count is stale.** STATUS.md line 44 says "11 of 21 operations." The capability
   registry shows 14 `StatusSupported` / 7 `StatusUnsupported` out of 21 — i.e. 14/21, not 11/21.
2. **16 registered services are entirely absent from STATUS.md's three curated tables** (Comprehensive /
   Core / Minimal-stub), appearing only in the bottom auto-generated op-count table with no
   characterization at all: ACM, Athena, Bedrock, CloudWatch, DynamoDB Streams, Firehose, Glue, OpenSearch,
   AppRegistry, Auto Scaling, Backup, CloudTrail, EKS, ELBv2, MSK, Organizations, Transfer Family. This
   plan independently classified all 16 by reading `internal/capabilities/all.gen.go`: Auto Scaling,
   Backup, CloudTrail, Transfer Family, and Organizations are wholly `StatusInert` (Tier 1); MSK is
   Docker-backed (Redpanda) and Core-depth already, comparable to RDS/ElastiCache; EKS has a live
   Docker-backed cluster mode (`internal/services/eks/live_runtime.go`) beyond pure metadata, but full pod-
   scheduling fidelity is XL-cost and low-fit (see §7); the remainder (ACM, Athena, Bedrock, CloudWatch,
   DynamoDB Streams, Firehose, Glue, OpenSearch, AppRegistry, ELBv2) are 100% or near-100%
   `StatusSupported` and effectively Core-depth already, just never added to the hand-written table.
3. **Pipes' "DDB→SQS only" claim (STATUS.md line 56) is accurate** — confirmed directly in
   [pipes/service.go:3-5](../../internal/services/pipes/service.go)'s own doc comment.
4. **IAM's "no enforcement" claim (STATUS.md line 32) is accurate** — confirmed in
   [iam/handler.go:1952](../../internal/services/iam/handler.go).
5. **Step Functions' "no execution engine yet" (STATUS.md line 55) is accurate** — confirmed in
   [stepfunctions/handler.go:224](../../internal/services/stepfunctions/handler.go).
6. **A claim this plan initially suspected but disproved**: S3 presigned URLs are *not* a gap.
   Query-string SigV4 auth (`X-Amz-Signature`) is handled generically for every service in
   [internal/middleware/sigv4.go](../../internal/middleware/sigv4.go), not per-service — presigned
   `GetObject`/`PutObject` URLs work today because presigning is a client-side SDK operation and the
   server only needs to validate the resulting query-string signature, which it already does. Not listed
   as a gap anywhere in this plan; recorded here so a future pass doesn't waste time re-investigating it.

STATUS.md itself should eventually be regenerated/rewritten to fold in the auto-generated capability data
directly rather than maintaining hand-written tables that drift — that's a separate, smaller piece of work
this plan flags but does not scope.

## 8. Living process — how this ranking gets refreshed

This document is a snapshot, not a contract. It should be re-derived, not just re-read, on the following
triggers:

1. **Capability registry drift.** `internal/capabilities/all.gen.go` is regenerated by `make generate-caps`
   and checked for staleness by `make check-caps` in CI — every service PR that adds/changes operations
   keeps it current. Before acting on any item in this backlog, re-check its `Status`/`Notes` rows there
   first; if a wave-1 item already shipped or its scope changed, this document is the one that's stale, not
   the code.
2. **Compat telemetry.** `compat/baseline.json` currently sits at zero failures by policy (`ci(compat):
   promote the baseline to zero failures, and gate on it absolutely`, #463) — it will not show
   "unimplemented" as a status. The live demand signal instead comes from `compat/parity-debt.json`
   (`go run ./cmd/compat --update-parity-debt`), which tracks which suites haven't wired up which
   registry groups yet, and from `compat/suites/registry.json` growing new groups/tests over time — a new
   registry group for a service/operation combination that didn't exist when this plan was written is a
   signal worth folding into the next revision's usage score. Once
   [compat-coverage-modelgen.md](./compat-coverage-modelgen.md)'s probe groups land, per-service
   `unimplemented` counts across eight suites become a *direct* demand-side telemetry feed for this
   ranking — the strongest of the triggers listed here.
3. **User issue reports.** Per STATUS.md's own convention, `// TODO(priority:Pn):` comments are
   auto-converted to GitHub issues. A cluster of issues against one service (e.g., several independent
   reports that EventBridge→Lambda doesn't fire) is a stronger usage signal than anything in §4 and should
   bump that item's priority on the next revision.
4. **Model-refresh diffs.** When the pinned AWS API model snapshot is updated (see
   [aws-api-operation-coverage.md](./aws-api-operation-coverage.md)), newly-appearing operations on
   already-registered services (AWS ships new API surface on existing services constantly) should be
   triaged into this backlog's waves rather than left to accumulate as undocumented 501s.
5. **Where this lives going forward**: this file, updated in place (not superseded by a new dated file)
   each time one of the above triggers fires a re-prioritization. Completed waves should be marked done
   inline (matching the `cf-update.md`/`dynamodb-gsi-design.md` convention of a status line that tracks
   per-item completion) rather than deleted, so the "why was this ordered this way" reasoning survives past
   the work landing. The backlog is also **mirrored to tracking issue #484** (one GitHub sub-issue per
   §3/Wave-4 item, in priority order); the two are mirrors and **must be updated together** — a
   re-prioritization that changes this document without re-ordering or re-scoping the tracked sub-issues is
   incomplete, and vice versa.
